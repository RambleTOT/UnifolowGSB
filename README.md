# UniFlow Analytics

Операционная видеоаналитика для университета: сколько людей вошло, сколько
вышло, сколько сейчас внутри и где возникают очереди.

Камер в этой версии нет: источник — предзаписанный видеофайл, который
воспроизводится по кругу и анализируется так же, как анализировался бы живой
поток. Система считает людей обезличенно: никакого распознавания лиц и никаких
признаков идентификации.

Документы:

- `docs/ACCURACY.md` — прогоны проверки подсчёта.
- `docs/DEVIATIONS.md` — расхождения с ТЗ, дизайном и заданием, с причинами.
- `docs/ACCEPTANCE.md` — приёмка: чек-лист ТЗ по пунктам и что осталось за рамками.
- `docs/CHECKS.md` — что и как проверялось на каждом этапе.

## Быстрый старт

```bash
make install          # окружение бэкенда
make install-web      # зависимости фронтенда
cp .env.example .env  # проверьте часовой пояс и ключ подписи
make demo-videos      # демонстрационные ролики в data/videos
make test             # тесты бэкенда
make dev              # бэкенд на :8000 и фронтенд на :5173
```

Интерфейс в разработке открывается на `http://localhost:5173` — запросы к API он
проксирует на бэкенд. Для сервера фронтенд собирается один раз
(`npm run build --prefix frontend`), после чего бэкенд отдаёт его сам на своём
порту.

При первом запуске создаётся учётная запись `admin`: если `UNIFLOW_ADMIN_PASSWORD`
в `.env` пуст, пароль генерируется и **один раз** печатается в консоль — сохраните
его. Сменить пароль можно командой:

```bash
cd backend && ../.venv/bin/python -m app.cli set-password --login admin
```

Тогда же создаются четыре источника из ТЗ (Столовая, Раздача, КПП 1, КПП 2).
Каждый видеофайл из `data/videos/` достаётся источнику, имя которого записано в
лежащей рядом разметке `<имя>.markup.json` полем `source`; файл без такого поля
получает первый источник, у которого видео ещё нет. Так после `make demo-videos`
первый же запуск даёт четыре считающих источника.

## Демонстрационные источники

Четыре камеры: две в столовой, две на КПП. Три из них — открытые ролики из
набора примеров Intel (`intel-iot-devkit/sample-videos`, Apache 2.0), которые
играют по кругу; четвёртая — прямой эфир публичной камеры. `make demo-videos`
скачивает ролики; сами файлы в репозиторий не входят, разметка к ним — входит.

| Источник | Контур | Что показывает | Что размечено |
|---|---|---|---|
| Столовая | столовая | `people-detection.mp4`, по кругу | линия входа, зона ожидания, зона зала |
| Раздача | столовая | `store-aisle-detection.mp4`, по кругу | линия раздачи, очередь к раздаче, зал раздачи |
| КПП 1 | КПП | `one-by-one-person-detection.mp4`, по кругу | основной проход, тамбур |
| КПП 2 | КПП | прямой эфир, камера на Дворцовой площади | поток через площадь, ближняя часть площади |

Всё это разворачивается само при первом запуске на чистой базе. Ролик
достаётся источнику, имя которого записано в разметке `<имя>.markup.json`
полем `source`. Прямой поток описан файлом `<имя>.stream.json`: та же разметка
плюс ссылка на поток и профиль модели. Свои источники добавляются так же или в
интерфейсе: «Источники видео» → «Добавить источник».

## Прямой поток с камеры

Кроме видеофайла по кругу, источник может смотреть живую камеру по ссылке —
HLS (`.m3u8`), RTSP или HTTP. В форме источника: «Прямой поток» → ссылка.

Пример, на котором это проверено, — публичная камера Эрмитажа на Дворцовой
площади, которую владелец сам опубликовал через «Видеонаблюдение» Ростелекома:

```
https://streamer.camera.rt.ru/public/master.m3u8?sid=ac4ad2e3-8615-4d5b-90dc-3f6a57d9a589
```

Что важно знать:

- **Эфир нельзя посчитать заранее**, поэтому анализ идёт только в реальном
  времени и нужен ускоритель. На Mac с Apple Silicon — 7–8 кадр/с при полном
  разрешении. На сервере без видеокарты с одним ядром живой анализ не потянет.
- **Для широкого плана — профиль «Дальний план»** (вход модели 1920). Люди на
  площади — 20–50 пикселей: при входе 960 модель находила 9 человек, при 1920 — 32.
- **Картинка идёт с задержкой около 25 секунд.** HLS приходит сегментами по
  5–15 секунд, и на каждой границе чтение замирает, пока скачивается следующий.
  Буфер выравнивает кадры по меткам времени потока, как обычный плеер, — без
  него трекер видел бы рывки и терял людей.
- **Обрыв связи источник переживает сам:** переподключается, а если кадров нет
  дольше 45 секунд, показывает «нет сигнала» с причиной.
- **Ссылка чужая и может измениться.** Для постоянной работы нужна своя камера
  или согласие владельца. Система хранит только счётчики и обезличенные треки,
  лица не распознаются.

## Что уже работает в интерфейсе

- Вход, каркас с восемью разделами, глобальные фильтры периода и контура в адресе страницы, индикатор состояния данных.
- Главная: путь первого запуска из трёх шагов, блок «что требует внимания», сводные показатели и список источников.
- Оперативный мониторинг: все источники сразу и детальный просмотр — изображение с наложением (рамки, номера треков, зоны, линии, вспышка засчитанного прохода), переключатели наложения, режимы «видео в реальном времени» и «точный анализ», диагностика одной фразой, воспроизведение файла с итогами кругов, текущие значения и техническое состояние.
- Источники: список с состоянием и параметрами, добавление и правка, загрузка видео с ходом выполнения и отменой, включение и выключение, проверка доступности, удаление с предупреждением о сохранении истории.
- Настройка зон и линий: кадр из любой точки файла, опорные точки людей, зоны очереди и заполненности, контрольные линии с разворотом направления, отмена и повтор, возврат к сохранённому, валидация с указанием проблемного объекта.

- Главная, Анализ очередей и Анализ КПП: показатели с направлением и оценкой изменения, графики потока и очередей с порогами, сравнение зон и проходов, тепловая карта, профиль по часам, сравнение по дням недели.
- История и события: журнал с фильтрами, сортировкой и страницами, массовые действия, выгрузка CSV и Excel, детали эпизода с динамикой вокруг события, кадром, историей обработки и сменой статуса.
- Уведомления в верхней панели и отдельная строка для критического события.
- Демо-режим: 30 суток синтетической истории по всем источникам, события собираются теми же правилами; наборы данных не смешиваются.

- Отчёты: параметры (контур или источник, период, детализация), предпросмотр со сводкой, табличной частью и приложением событий, выгрузка в PDF, Excel и CSV. Файл всегда совпадает с предпросмотром: при смене параметров он помечается устаревшим.
- Настройки: системные параметры анализа, пороги событий и хранение — с пояснениями, границами, пометкой изменённых полей и сбросом к исходным; личные — профиль, режим данных, имя, автообновление.
- Поиск по источникам, событиям и разделам — с клавиатуры, с группировкой результатов.

| Живая часть | `GET /api/sources/{id}/stream.mjpg`, `…/snapshot.jpg`, `…/analysis.jpg`, `WS /ws/sources/{id}`, `WS /ws/system` |
| Настройки | `GET/PUT /api/settings`, `POST /api/settings/reset` |
| Аналитика | `GET /api/dashboard`, `/api/analytics/queues`, `/api/analytics/checkpoints`, `/api/sources/{id}/summary` |
| События | `GET /api/events`, `GET /api/events/{id}`, `POST …/status`, `POST /api/events/bulk-status`, `GET /api/events/export`, `GET …/snapshot` |
| Уведомления | `GET /api/notifications`, `POST /api/notifications/seen` |

| Отчёты | `POST /api/reports/preview`, `POST /api/reports/export` |
| Поиск | `GET /api/search?q=` |

Изображение и наложение идут разными путями: браузер получает кадры потоком, а
рамки, зоны, линии и засчитанные проходы — сообщениями по веб-сокету. Поэтому
переключатели наложения работают мгновенно.

## Проверка подсчёта на видео

```bash
python scripts/evaluate.py \
  --video data/videos/<файл>.mp4 \
  --markup data/videos/<файл>.markup.json \
  --output data/videos/<файл>.annotated.mp4
```

Скрипт печатает, сколько входов и выходов насчитала система, и сохраняет
размеченный ролик: рамки людей, номера треков, опорные точки, зоны, линия,
вспышка в момент засчитывания прохода и бегущие счётчики. Это тот же код
подсчёта, что работает в приложении.

Разметка — файл JSON с координатами, нормированными к кадру (0..1):

```json
{
  "anchor": "bottom_center",
  "lines": [
    {"id": "line-main", "name": "Основной проход",
     "a": [0.15, 0.55], "b": [0.85, 0.55],
     "entry_side": -1, "counts": "both"}
  ],
  "zones": [
    {"id": "zone-queue", "name": "Очередь", "kind": "queue",
     "min_dwell_seconds": 5,
     "polygon": [[0.1, 0.6], [0.6, 0.6], [0.6, 0.95], [0.1, 0.95]]}
  ]
}
```

`entry_side` — знак стороны линии, переход на которую считается входом:
`-1` — сторона меньших `y` (верх кадра), `1` — сторона больших `y`.

## Развёртывание на сервере

С машины разработчика, одной командой (нужен вход на сервер по SSH-ключу и
Docker с Compose на сервере):

```bash
scripts/deploy.sh root@<адрес-сервера>
```

Скрипт копирует код в `/opt/uniflow`, докладывает демо-ролики, веса модели и
готовые кэши предрасчёта (сервер не пересчитывает ролики заново), при первом
запуске создаёт `.env` с новым ключом подписи и самоподписанный сертификат,
затем собирает и поднимает два контейнера:

- `uniflow` — приложение; наружу не публикуется;
- `edge` — nginx на портах 80 и 443: HTTPS, WebSocket, видеопоток без
  буферизации, загрузка видео до 512 МБ.

Сборка идёт на сервере отдельно от SSH-сессии: если соединение оборвётся,
она доработает сама. Повторный запуск обновляет код и пересобирает образ;
база, загруженные через интерфейс видео, `.env` и сертификат не трогаются.

Пароль первой учётной записи печатается один раз в журнал приложения:

```bash
ssh root@<адрес-сервера> "cd /opt/uniflow && docker compose logs uniflow | grep Пароль"
```

Сертификат самоподписанный — адрес без домена. Браузер один раз попросит
подтвердить исключение. С доменом его можно заменить на Let's Encrypt, поменяв
только файлы в `deploy/certs/`.

## Лицензия

Для детекции используется Ultralytics YOLO под лицензией AGPL-3.0: проект,
выложенный в сеть, должен быть открыт под совместимой лицензией. Для учебного
и демонстрационного проекта это допустимо. Детектор скрыт за интерфейсом
`Detector` (`backend/app/cv/detector.py`), поэтому его можно заменить на модель
с разрешительной лицензией, например RF-DETR (Apache 2.0).
